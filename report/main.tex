\begin{abstract}
Academic advising requires institution-specific and version-sensitive information, including degree requirements, course classifications, prerequisites, schedules, and student history. General-purpose large language models may answer such questions fluently while relying on outdated or unsupported information. This paper presents SU-GPT, a retrieval-augmented academic advising assistant for Sabancı University students. The system combines a React interface, a FastAPI backend, MongoDB for structured application state, ChromaDB for semantic retrieval, MiniLM embeddings, BM25 lexical retrieval, cross-encoder reranking, and an API-hosted LLM.

The stable curated catalog corpus used in the broader system evaluation contains 14,242 academic records generated from course catalog, program classification, schedule, graduation, and degree-requirement JSONL files. We evaluate SU-GPT with intent-routing tests, retrieval ablations, manual end-to-end answer review, and a reproducible Section 5/6 benchmark pipeline. In the broader evaluation, intent routing achieved 66.67\% accuracy, structured retrieval improved Recall@10 from 13.33\% for pure dense search to 30.00\%, and cross-encoder reranking improved MRR from 0.1924 to 0.1995. Manual end-to-end review produced 37.50\% normalized answer correctness with a mean response latency of 14.93 seconds. The new local evaluation runner additionally produced JSONL/CSV artifacts for a 68-question benchmark and Section 6 ablation smoke tests. A three-mode Section 6 run over two questions at top-$k=3$ found BM25 strongest on that small slice: Recall, MRR, nDCG, and hit rate were all 1.0 for BM25, 0.5 for dense retrieval, and 0.0 for hybrid rerank. The combined evaluation shows that SU-GPT is a functional course-aware RAG system, but reliable advising requires stronger course-code normalization, metadata filtering, short-chunk handling, and deterministic degree-audit logic.
\end{abstract}

\section{Introduction}

University students regularly ask which courses remain compulsory, whether a course counts as an area or free elective, which sections are offered, who teaches a course, whether a prerequisite applies, and what they should take next. Correct answers require combining official curriculum rules, course descriptions, program-specific classifications, schedules, credit constraints, and the student's academic history.

A general-purpose LLM cannot be expected to contain accurate and current information for every university curriculum. Even when its response is fluent, it may use outdated knowledge or silently apply the wrong curriculum year. Retrieval-augmented generation (RAG) addresses this problem by retrieving relevant external documents and providing them to the generator as context \cite{lewis2020rag}.

We developed SU-GPT as a domain-specific RAG application for Sabancı University. It retrieves information from course, curriculum, graduation, schedule, and course-material records. It also loads the authenticated user's selected courses from MongoDB to personalize answers and avoid recommending completed courses. The project belongs primarily to the Application/System Building category and secondarily to Evaluation/Analysis.

The contributions are:
\begin{itemize}
    \item an end-to-end academic advising application connecting a React frontend, FastAPI, MongoDB, ChromaDB, local retrieval models, and an API-hosted LLM;
    \item a production-oriented data design in which MongoDB is the durable source of truth and ChromaDB is a rebuildable vector index;
    \item deterministic source and chunk identifiers for reproducible ingestion and evaluation;
    \item a unified retrieval-mode contract covering \code{llm\_only}, BM25, dense, dense rerank, hybrid, and hybrid rerank modes;
    \item a reproducible benchmark runner that writes \code{results.jsonl}, \code{retrieved\_chunks.jsonl}, \code{summary\_metrics.json}, and report-ready CSV tables;
    \item an honest failure analysis and a data roadmap for supporting multiple programs and curriculum years without mixing incompatible sources.
\end{itemize}

\section{Background}

\subsection{Retrieval-Augmented Generation}

RAG combines information retrieval and language generation. Instead of asking an LLM to answer solely from its parameters, a retriever first identifies documents related to the question. These documents are inserted into the prompt so the generator can produce a grounded response \cite{lewis2020rag}. This architecture is appropriate for institutional information that changes over time or is absent from public model training data.

\subsection{Dense Retrieval and Reranking}

Dense retrieval represents documents and queries as numerical vectors. Semantically related texts are expected to be near each other in the embedding space. Sentence-BERT provides efficient sentence-level representations for semantic search \cite{reimers2019sentencebert}. SU-GPT uses \code{all-MiniLM-L12-v2}, a compact 384-dimensional embedding model.

Bi-encoders encode the query and document independently. Cross-encoders instead process a query-document pair jointly and often provide better relevance estimates at greater computational cost \cite{nogueira2019passage}. SU-GPT first retrieves a candidate set and can then use \code{cross-encoder/ms-marco-MiniLM-L-6-v2} to rerank it.

\subsection{Dense, Lexical, and Hybrid Search}

BM25 is a lexical retrieval method based on exact term occurrences and document statistics \cite{robertson2009bm25}. Hybrid retrieval combines lexical and dense search. This matters for academic advising because course identifiers such as ``CS412'' or ``CS 412'' are symbolic facts, not merely semantic phrases. The current codebase includes BM25, dense, dense-rerank, hybrid, and hybrid-rerank modes through a shared \code{run\_retrieval\_mode} contract. Hybrid search fuses lexical and dense candidates using reciprocal-rank fusion (RRF) \cite{cormack2009rrf}.

\section{System Architecture}

SU-GPT consists of a frontend, backend, operational database, vector database, local retrieval models, and a remote generator.

\input{figures/architecture}

\subsection{Frontend and Backend}

The frontend is implemented using React and Vite. It provides the chat interface, authentication view, course-selection menu, and document-upload controls. During local development it runs at \code{http://localhost:5173}. The backend is implemented with FastAPI and normally runs at \code{http://127.0.0.1:8000}. The \code{/ask/} endpoint receives a question and optional username, resolves intent, constructs a retrieval query, retrieves and reranks documents, loads user context, builds the prompt, invokes the LLM, and returns the answer with sources and source chunk IDs.

LangChain connects document objects, embedding models, ChromaDB, retrievers, prompts, and the LLM chain. It is an orchestration library rather than a model or database. The generator provider is configurable; the codebase includes Groq/Llama and Mistral-ready settings.

\subsection{MongoDB Source of Truth}

MongoDB stores structured application state. The database includes collections for users, courses, user-course links, upload batches, source documents, ingestion jobs, instructor reviews, exams, and embedding-cache records. When a user selects completed courses, the backend stores links between the user and course records. For recommendation questions, the selected courses are inserted into the prompt as an exclusion list. For graduation questions, their SU credits can be summed and passed to the answer pipeline.

MongoDB is not used for semantic retrieval. ChromaDB is treated as a reproducible vector index that can be rebuilt from durable MongoDB source metadata and source files.

\subsection{ChromaDB}

ChromaDB stores retrieval-ready text, vector embeddings, metadata, and stable chunk identifiers. The persistent collection is named \code{su\_knowledge}. Metadata can contain the document type, course code, program, academic term, requirement category, source path, and source authority. The current benchmark-relevant corpus intentionally contains no review, exam, or syllabus-specific source documents; those domains are answered with explicit source-availability caveats rather than fabricated retrieved evidence.

\subsection{Information Cards, Chunking, and Ingestion}

The ingestion pipeline converts structured rows into explanatory information cards. A classification row becomes a short text stating the program, term, course, category, SU credits, ECTS, engineering ECTS, and basic science ECTS. Long uploaded documents are cleaned and split into chunks. Structured JSONL records generally become self-contained cards rather than arbitrary fragments.

Every chunk receives a deterministic ID:

\begin{center}
\code{sourceId:chunkIndex:contentHashPrefix}
\end{center}

For example, the local benchmark contains verified chunk IDs such as:

\begin{center}
{\scriptsize\code{course:5a6a448569ef18c6d8137810:150:5f9083e5db8d5499}}
\end{center}

These IDs make chunk-level Recall@K, MRR@K, and nDCG@K reproducible.

\section{Question-Answering Pipeline}

\subsection{Intent Routing}

The system first predicts or resolves an intent. The current routes include graduation status, course recommendation, study plan, major selection, specialization, course detail, review, exam, and general fallback. The resolved intent controls retrieval expansion, source filtering, and prompt style.

If local evidence is intentionally absent, as for review, exam, and syllabus-specific corpora in this phase, SU-GPT should not claim to have retrieved private evidence. Instead, it should say that the project is still missing that source type and then give cautious general guidance. For an instructor-review query, for instance, the assistant can suggest checking student groups or emailing the instructor with a concise background and question, while clearly marking that no local review archive was used.

\subsection{Retrieval and Generation}

The query is optionally expanded based on intent. The catalog retriever extracts course codes, terms, program codes, and requirement-category terms. It then attempts exact metadata lookup, filtered dense search, BM25 search, or hybrid search depending on the selected retrieval mode. Candidate documents are deduplicated and may be reranked with a cross-encoder. The default final context size in the local benchmark runner is $k=6$; the Section 6 ablation run used $k=3$.

The backend retrieves selected courses from MongoDB. For recommendations, these courses are marked as already completed so they are not suggested again. The generator is instructed to answer in the user's language, use retrieved Sabancı-specific information where available, cite sources, and avoid unsupported official-advising claims.

\section{Evaluation Methodology}

\subsection{Research Questions}

The evaluation investigates:
\begin{enumerate}
    \item How accurately does the router identify unseen Turkish questions?
    \item Do structured filters and lexical heuristics improve over pure dense Chroma search?
    \item Does cross-encoder reranking improve candidate ordering?
    \item Does the full system return correct and properly sourced answers?
    \item What are the dominant failure modes and latency costs?
    \item How do BM25, dense retrieval, and production-style hybrid rerank behave in a small reproducible Section 6 ablation?
\end{enumerate}

\subsection{Evaluation Sets}

The broader system evaluation used three sets:
\begin{itemize}
    \item 42 unseen Turkish intent queries, six for each of the seven base intents;
    \item 30 retrieval queries with gold metadata predicates covering course catalog, program classification, schedule, and degree-requirement questions;
    \item 12 end-to-end questions submitted through the real API and manually reviewed for correctness.
\end{itemize}

\subsection{Metrics}

Retrieval is measured with Recall@K, MRR@K, and nDCG@K. Chunk-level matching is used when \code{expected\_chunk\_ids} exist. If a row has no expected chunk IDs, the evaluator falls back to source-level matching using \code{expected\_sources}.

\begin{align}
\mathrm{Recall@K} &= \frac{|\mathrm{Retrieved}_{1:K} \cap \mathrm{Gold}|}{|\mathrm{Gold}|},\\
\mathrm{MRR@K} &= \frac{1}{\mathrm{rank\ of\ first\ relevant\ hit}},\\
\mathrm{nDCG@K} &= \frac{\mathrm{DCG@K}}{\mathrm{IDCG@K}}.
\end{align}

End-to-end answers in the broader manual review were scored as 0 for incorrect/unsupported, 1 for partially correct, and 2 for fully correct and grounded. The automated local runner leaves answer-correctness fields blank until manual or automated grading is actually performed.

\section{Error Analysis}
\label{sec:error-analysis}

\subsection{Course-Code Inconsistency}

Course-catalog and basic-science metadata often use compact identifiers such as \code{CS300}, while program and schedule records use \code{CS 300}. If the query extractor produces only one format, exact filters can miss valid documents. This is the most important low-level retrieval bug because course identifiers are central to the domain.

\subsection{Over-Constraining Metadata Filters}

The retriever can interpret \code{CS} both as a program code and as the subject of a course code. If it adds \code{program=CS} to schedule filters, correct schedule documents may be removed because schedule records do not contain the same program field. The broader evaluation found this pattern in schedule failures.

\subsection{Ambiguous Keyword Routing}

The word \code{program} can refer to a degree program, a term snapshot, or a schedule-like listing. Course-detail query expansion can also add schedule-oriented terms even when the user asks about a prerequisite or description. These ambiguities can steer retrieval toward the wrong document type.

\subsection{Short Chunk Weakness}

The local Section 6 failure file contains a q020 case where the gold slide title chunk was very short. Neighboring chunks with more text outranked the exact slide-title chunk. A practical fix is to merge very short slide-title chunks with neighboring context or add title/slide-number boosts for slide-specific questions.

\subsection{Sample Degree Evaluation Leakage}

The CS degree-requirement file contains a sample degree-evaluation projection with completed courses and 125 credits. If globally indexed, the LLM can present this sample student's completed categories as if they answer a generic graduation question. Student-specific degree evaluations should be private MongoDB records or access-controlled vector records, not shared curriculum knowledge.

\section{Limitations and Future Work}

SU-GPT is not yet reliable as an official multi-program degree advisor. Detailed requirements are available only for CS curriculum 202101. User profiles need major, degree code, admission term, curriculum term, current term, minor codes, course status, transfer status, repeated-course handling, and withdrawal status.

Academic arithmetic should move from the LLM into a deterministic degree-audit module. It should apply equivalencies, choice pools, category allocation, overflow rules, repeated-course handling, total SU credits, ECTS, engineering ECTS, basic-science ECTS, and GPA constraints. The LLM should explain the computed result without altering it.

Immediate retrieval improvements include:
\begin{itemize}
    \item normalize compact and spaced course identifiers during ingestion and querying;
    \item avoid treating a course subject as a program filter for schedule and catalog sources;
    \item select document-type filters from the original intent rather than keywords introduced by query expansion;
    \item enrich very short slide-title chunks with neighboring context;
    \item separate current classifications, curriculum requirements, schedules, shared documents, and private student documents;
    \item run the full 68-question, six-mode benchmark and manually grade answer correctness fields;
    \item add official syllabus sources before claiming syllabus-specific support.
\end{itemize}

\section{Ethical Considerations and AI Disclosure}

Academic advice can affect important student decisions. SU-GPT should not claim that a student can graduate unless the result uses the correct official curriculum and a complete academic record. Answers must remain advisory and direct students to the official Degree Evaluation and academic advisors for confirmation.

Course histories and uploaded degree evaluations are personal academic data. Future versions should enforce authentication, ownership filters, access control, and deletion policies. Private student documents must never be retrievable by another user.

Generative AI tools were used as development assistants for codebase analysis, debugging, dependency configuration, documentation, evaluation tooling, and report drafting. The project members remain responsible for reviewing the code, running the experiments, checking source data, and validating all reported results. The numerical values in this report come from measured output files or explicitly reported evaluation runs; they were not fabricated by the generator.

\section{Conclusion}

SU-GPT demonstrates a complete retrieval-augmented academic advising application integrating institutional academic data, vector retrieval, lexical retrieval, cross-encoder reranking, MongoDB student history, and LLM generation. The broader evaluation shows that structured retrieval substantially improves over pure dense search, increasing Recall@10 from 13.33\% to 30.00\%, while cross-encoder reranking improves MRR to 0.1995. Manual end-to-end answer quality remains limited at 37.50\% normalized correctness, showing that a working interface and successful API calls do not guarantee reliable advising.

The local Section 5/6 tooling adds reproducibility: the project now writes retrieval metrics, latency, cost estimates, ablation summaries, and seed failure cases to committed output files. The dominant errors occur before generation: inconsistent identifiers, incorrect metadata constraints, missing or short chunks, and ambiguous routing remove the correct evidence from the candidate set. These findings define the next engineering direction: curriculum-aware metadata, versioned official data, deterministic degree auditing, normalized identifiers, and exact lexical safeguards are necessary before SU-GPT can be trusted as an official advising assistant.
